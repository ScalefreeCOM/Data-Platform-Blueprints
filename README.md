# Data Platform Blueprints: Industry Architectures, Sovereignty and Cloud

Scalefree data platform blueprints for 66 industries: sovereign Data Vault architectures and cloud implementations on Snowflake, Databricks, Microsoft Fabric and Google BigQuery. Each connects real industry workflows to source data, business rules, governance, deployment, training and measurable operating cost.

This collection contains **335 self-contained blueprints**: 66 sovereign industry blueprints, 264 cloud industry blueprints (four platforms for each of 66 industries), and five technology blueprints. A further **66 platform selection guides** compare the industry options. Each document contains its implementation guidance, training plan, source links, and Next steps.

## Choose a starting point

| Series | Main decision | What the blueprint provides |
| --- | --- | --- |
| Sovereign industry | How should we retain control over data, processing, administration, portability, and exit? | A real industry workflow, worked calculation, Data Vault entities, domain controls, pilot, and open-source-first implementation on Azure, AWS, or Google Cloud. |
| Cloud industry implementation | Which managed platform offers the best fit for our workload, team, delivery targets, and lifecycle cost? | One industry and one selected platform, with a tailored flow diagram, physical design, ingestion contract, workload benchmark, TCO drivers, and operating design. The selection guide compares the four platforms. |
| Technology | How should we implement and operate a selected platform? | Platform-specific architecture, table/compute choices, integration, cost drivers, recovery, migration, and acceptance evidence. |

Sovereignty and managed-cloud value are complementary decision dimensions. The cloud series prioritizes delivery speed, managed capability, elasticity, and useful platform integration. It retains privacy, security, contractual, and operational requirements. TCO is measured across implementation, consumption, licenses, staffing, recovery, and exit; a newer feature earns its place through a concrete use case and a validated benefit.

Platform recommendations are workload hypotheses, not universal industry rankings. Read the assumptions in each document before adopting a recommendation. An organization's cloud estate, skills, data gravity, service availability, pricing agreement, and operating capacity can change the decision.

## Common implementation language

The modeling chain is **Flow.BI → FCT → TurboVault → generated-model review → datavault4dbt/dbt execution**. Users extend the overall model through additional **Business Vault entities**. **dlt** supplies code-managed ingestion; **Fivetran** supplies commercial managed replication where the source and destination are supported. Fivetran is primary in 165 of the 264 standalone cloud industry blueprints (62.5%): all Snowflake and BigQuery editions, and half the Databricks editions. dlt is primary in the other 99, including every Fabric edition. The 66 comparison guides retain 34 Fivetran and 32 dlt reference stacks. Sovereign industry editions retain dlt. Specialized source protocols require appropriate interfaces or gateways.

Flow.BI requires actual source data; source metadata is mostly optional and improves results. Its local-processing Docker image runs in customer-controlled Azure, AWS, or Google Cloud infrastructure. Derived metadata and statistical fingerprints use an approved connection to the Flow.BI backend.

**DWA** means Data Warehouse Automation. **DVA** refers exclusively to the Data Vault Alliance. The training sections include Data Vault, DWA/dbt, and Flow.BI learning paths. The documents link to Scalefree and Flow.BI implementation material and primary industry/platform references.

## PostgreSQL, Cloudberry and sovereign warehouse scale

Plain PostgreSQL is an option for a bounded pilot or suitably small workload with measured growth and recovery limits. For a larger relational Data Vault, the sovereign series evaluates **Apache Cloudberry**: PostgreSQL/Greenplum compatibility preserves familiar integration routes, MPP distributes analytical work across segments, and each table can use row-oriented or column-oriented storage according to its access/write pattern. Iceberg/Trino remains the portable lakehouse alternative.

Read [Architectural Limitations of PostgreSQL for Enterprise Data Vault Workloads](https://www.scalefree.com/blog/data-vault/architectural-limitations-of-postgresql-for-enterprise-data-vault-workloads/) alongside the [Apache Cloudberry blueprint](cloud/apache-cloudberry/apache-cloudberry-data-platform-blueprint.md). Benchmark history queries, joins, corrections, concurrent reporting, distribution skew and recovery; a successful small PostgreSQL pilot is not a large-scale sizing result.

## Use a blueprint in a project

1. Choose the industry document closest to the actual workflow and identify a business owner.
2. Define source scope, grain, calculation, access, reporting cutoff, and reconciliation evidence.
3. Select the sovereignty emphasis or use the cloud selection guide, then open the chosen platform implementation and test it against the strongest alternative.
4. Run the worked example and failure cases using representative, authorized data.
5. Demonstrate historical reconstruction, permissions, recovery, regeneration, and operating cost before expanding.

The worked numbers are illustrative, and the proposed controls and acceptance measures need project-specific targets. Apply the relevant legal/regulatory and professional requirements to the actual organization and jurisdiction. Pin the tool versions and verify integrations against those versions.
